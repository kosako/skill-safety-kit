# skill-safety-kit

Agent Skill(Claude Code / Claude Cowork の「AI への作業手順書」)を配布・共有する前に、
**安全性・品質・コンプライアンス**を点検するためのスキル集と解説ドキュメントです。
組織での運用(チームでスキルを作って配る場面)向けに用意しています。

スキルを作って配る運用が広がると、「そのスキルは安全か」「良いスキルか」を
見極める手立てが要ります。このキットはそれを、スキル自身の力で行います。

## 含まれるもの

### スキル 2 本(`skills/`)

| スキル | 役割 |
| --- | --- |
| [**skill-check**](skills/skill-check/SKILL.md) | スキルを 1 個ずつ点検し、安全性・構造・権限とデータの扱い(コンプライアンス)・発火品質・「そもそも skill にする価値」の観点でレビューして、配布可否を判定する |
| [**skill-portfolio-audit**](skills/skill-portfolio-audit/SKILL.md) | インストール済みスキル全体を棚卸しする(多すぎ/重複/未使用/skill 化候補) |

どちらも **点検してレポートを返すだけ**で、勝手に修正・削除・配布はしません。

### ドキュメント(`docs/`)

- [**スキルの安全チェック ガイド**](docs/skill-governance-guide.md) — 非エンジニア向け。概念・使い方・判定の読み方・運用の約束ごと・FAQ。
- [**スキルを狙う攻撃カタログ**](docs/attack-catalog.md) — 読み物。14 種の攻撃手口を「狙い / 例 / 検知 / 注意点」で解説。

### 検証コーパス(`test-corpus/`)

回帰テスト・受け入れ確認用の検証 fixture。詳細は [test-corpus/README.md](test-corpus/README.md)。

- `attacks/`(10 種)— 検知できるべき攻撃スキルの無害ダミー
- `benign/`(10 種)— 誤検知(false positive)しないか確認する良性スキル

## 使い方

### 1. スキルとして読み込ませる(Claude Code)

Claude Code のスキルは `~/.claude/skills/<スキル名>/SKILL.md` に置くと、全プロジェクトで
使えるようになります(そのプロジェクトだけで使うなら `<プロジェクト>/.claude/skills/` へ)。
このキットの 2 スキルを取り込むには、フォルダごとコピーします。

```sh
# このリポジトリを取得
git clone https://github.com/kosako/skill-safety-kit.git
cd skill-safety-kit

# ユーザーレベル(全プロジェクトで使える)に配置
mkdir -p ~/.claude/skills
cp -R skills/skill-check          ~/.claude/skills/
cp -R skills/skill-portfolio-audit ~/.claude/skills/
```

配置後の確認と使い方:

- **認識**: `SKILL.md` の編集はセッション中に反映されますが、`~/.claude/skills/` を**新しく
  作った場合は Claude Code を再起動**(新セッション)すると認識されます。
- **確認**: `/skills` でスキル一覧を見る、`/doctor` で読み込み状況を見る、あるいは
  「どんなスキルが使える?」と聞く。
- **呼び出し**: `/skill-check` と明示的に打つか、依頼内容が description に合致すれば自動発火します。
- 同梱の `references/` や `evals/` はそのまま入れて問題ありません(入口は `SKILL.md` だけで、
  他のファイルは必要になったときだけ読まれます)。

### 2. 点検を依頼する

読み込ませたら、点検したいスキルを渡して普通に頼むだけです。

- 「このスキルをチェックして」(フォルダ・ファイル・公開スキルの URL を渡す)
- 「スキルが更新されたので再チェックして」
- 「入っているスキルの棚卸しをして」

判定は **配布可 / 人のレビュー必須 / 配布不可 / 判定不能** の 4 種。読み方は
[ガイド](docs/skill-governance-guide.md)を参照してください。

### 3. 配備までの流れ(例)

チームの誰かが作った新しいスキル(`./new-skill/`)を、組織全体へ配るまでの一例です。

```
1. 点検を依頼する
   「./new-skill をチェックして」
      ↓
2. レポートの総合判定を見る
   ├─ 配布不可     → 作者に修正を依頼 → 直ったら 1 に戻って再チェック
   ├─ 人のレビュー必須 → 詳しい人(エンジニア)が確認し、OK なら次へ
   ├─ 判定不能     → 全ファイルを揃える/検査できる環境で 1 をやり直す
   └─ 配布可       → 次へ(改善提案があれば目を通す)
      ↓
3. 自組織の管理下へ取り込む(vendoring)
   - 外部スキルを直接参照でインストールさせない。レビュー済みの中身を
     組織の管理リポジトリ等へコピーする。
   - このとき取得元(URL / commit SHA)と内容ハッシュをレポートから控えておく。
      ↓
4. チームへ配備する
   - 各メンバーの ~/.claude/skills/ へ配る(dotfiles / 配布の仕組みに載せる)。
      ↓
5. 更新が来たら 1 からやり直す
   - 差分だけでなくフルで再チェック。内容ハッシュが変わったら以前の合格は失効。
```

ポイントは **「チェックしてから取り込み、直接参照しない」「更新のたびに再チェック」** の 2 つです
(理由はサプライチェーン攻撃対策。下記)。

## 導入時の推奨(サプライチェーン対策)

外部の公開スキルは**直接参照のまま使わず**、レビュー後に自組織の管理下へ取り込み
(vendoring)、そこから配ることを推奨します。更新のたびに再チェックしてください
(このリポジトリ自体も、そうやって取り込んで使う想定です)。

## 検証状況

- 攻撃検知: held-out + 調査由来の novel、計 10 種を実レビューで全て捕捉、injection 追従ゼロ。
- 誤検知: 良性 10 種で「配布不可」ゼロ。
- author≠reviewer の相互レビュー(Codex)を複数ラウンド、最終 must 0。

チェックは見落としを減らす道具であって、安全の保証ではありません。権限設定・サンドボックス・
自動更新の停止といった実行環境側の守りと併用してください。
